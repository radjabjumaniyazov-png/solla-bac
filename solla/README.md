# Solla — backend skeleton

## Запуск

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env      # при желании поменять SECRET_KEY
uvicorn app.main:app --reload
```

Откройте http://127.0.0.1:8000/docs — интерактивная документация (Swagger),
там можно вызвать все эндпоинты руками, не дожидаясь фронтенда.

## Что уже готово

- **Модели данных** (`app/models.py`) под все разделы ТЗ: users, contacts,
  blacklist, groups/group_members, channels/channel_subscribers, messages
  (универсальная таблица для чатов/групп/каналов).
- **Регистрация и логин** (`POST /auth/register`, `POST /auth/login`) —
  bcrypt-хеширование пароля, JWT-токен на час.
- **Профиль/настройки** (`app/routers/profile.py`) — смена имени, аватарки,
  пароля, юзернейма, управление чёрным списком. Покрывает вкладку 5 из ТЗ.
- **Контакты** (`app/routers/contacts.py`) — поиск по юзернейму, добавление,
  список, удаление. Покрывает вкладку 2 из ТЗ.
- **Группы** (`app/routers/groups.py`) — создание (сразу с приглашением
  участников по юзернейму), список своих групп, добавление/удаление
  участников, роли owner/admin/member. Владелец группы неудаляем и роль
  ему сменить нельзя. Покрывает вкладку 3.
- **Каналы** (`app/routers/channels.py`) — создание (с опциональным публичным
  @username), подписка/отписка, поиск, `/channels/recommended` — заготовка
  под блок «Рекомендованные каналы» (сейчас возвращает каналы с флагом
  `is_recommended=True`; реальный алгоритм подбора — на потом). Владелец
  может назначать/снимать админов. Покрывает вкладку 4.
- **Сообщения** (`app/routers/messages.py`) — REST для истории
  (`GET /messages/direct/{username}`, `/messages/group/{id}`,
  `/messages/channel/{id}`, с пагинацией через `before_id`),
  `GET /messages/conversations` — список диалогов для вкладки «Чаты»
  (собеседник + последнее сообщение, отсортировано по свежести), и
  **WebSocket** (`ws://.../ws?token=...`) для мгновенной доставки.
  Покрывает вкладку 1 — и на фронтенде уже подключена целиком, включая
  экран открытой переписки с реальным обменом сообщениями.

### Права доступа к сообщениям

| Тип чата | Кто может писать | Кто получает |
|---|---|---|
| Личный (direct) | любая сторона, если не в ЧС друг у друга | оба участника, на все свои устройства |
| Группа | любой участник (member/admin/owner) | все участники группы |
| Канал | только owner и admin канала | все подписчики канала |

Проверка прав происходит **на сервере при каждой отправке** (не только в
интерфейсе), поэтому подделать запрос с фронтенда и написать в чужой канал
не получится — сервер отклонит и вернёт `{"error": "..."}` в тот же сокет.

### Как работает WebSocket

Один эндпоинт `/ws` на всех: клиент подключается один раз после логина и
дальше через него же отправляет сообщения в любые чаты (direct/group/channel)
и получает входящие — не нужно открывать отдельный сокет на каждый чат.

Формат исходящего сообщения от клиента (JSON):
```json
{"chat_type": "direct", "to_username": "bob", "text": "привет"}
{"chat_type": "group", "group_id": 1, "text": "привет всем"}
{"chat_type": "channel", "channel_id": 1, "text": "новость"}
```
Сервер в ответ рассылает всем адресатам (включая отправителя — это
синхронизация между его собственными устройствами) JSON вида `MessageOut`
с `id`, `sender_username`, `text`, `created_at`.

Аутентификация — токен в query-параметре (`?token=...`), потому что
браузерный WebSocket API не поддерживает кастомные заголовки при подключении
(в отличие от обычных HTTP-запросов, где токен идёт в `Authorization`).

Реализация — in-memory (`app/ws_manager.py`), рассчитана на один инстанс
сервера. Если позже появится несколько инстансов за балансировщиком, здесь
нужно будет добавить Redis pub/sub, чтобы сообщения долетали до сокетов,
подключённых к другому инстансу — сам API эндпоинтов при этом не изменится.

### Проверка вручную (сеть в моей песочнице отключена, поэтому сам живой сервер я не поднимал)

```bash
uvicorn app.main:app --reload      # в одном терминале
pip install websockets requests
python scripts/ws_smoke_test.py    # в другом — увидите мгновенную доставку
```

Либо просто откройте `/docs`, залогиньтесь через `/auth/login`, скопируйте
токен и подключитесь к `/ws?token=...` через любой WebSocket-клиент
(например, расширение для Chrome или `websocat`).

Проверка уникальности логина и юзернейма — на двух уровнях: в Pydantic-схеме
(формат) и в БД (UNIQUE-индекс + явная проверка перед вставкой), так что race
condition при одновременной регистрации тоже отловится (БД вернёт ошибку
целостности, если два запроса проскочат проверку одновременно — это стоит
обернуть в try/except IntegrityError, когда дойдём до нагрузочного тестирования).

## Что осталось (следующие шаги)

1. **Загрузка файлов** (аватарки, вложения в чатах) — эндпоинт с
   `UploadFile`, хранение на диске или в S3-совместимом сторадже.
2. **Alembic** — как только схема БД начнёт меняться на реальных данных,
   `Base.metadata.create_all` перестанет годиться (он не умеет ALTER TABLE).
3. **Тесты** — pytest + httpx.AsyncClient, отдельная тестовая БД в памяти.
4. **Frontend**: экран логина/регистрации, затем 5 вкладок по ТЗ — это
   следующий шаг, к нему и переходим.

## Структура проекта

```
app/
  main.py           # точка входа, регистрация роутеров, CORS
  database.py        # подключение к SQLite/PostgreSQL
  models.py          # SQLAlchemy-модели
  schemas.py          # Pydantic-схемы запросов/ответов
  auth.py             # хеширование паролей, выдача и проверка JWT
  routers/
    auth.py           # /auth/register, /auth/login
    profile.py         # /profile/*
    contacts.py         # /contacts/*
```
